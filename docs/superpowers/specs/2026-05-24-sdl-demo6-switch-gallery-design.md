## 1. 文档目标

本文件用于定义一个新的 SDL 示例 demo：

> **新增 `USE_DEMO == 6` 的独立控件 gallery，用鼠标水平滑动逐页查看单个控件，第 1 页固定展示 `switch`。**

本轮设计的核心前提已经由用户确认：

- 现有 `demo2` 必须保持不变
- 新能力必须以独立 demo 的方式接入，而不是改写现有 widget demo
- 新 demo 的翻页方式必须是鼠标滑动，而不是自动轮播
- 每页只放一个主控件
- 控件顺序按“控件类型”重排，而不是沿用 `demo2` 当前出现顺序

本 spec 的目标不是做一个新的控件系统，而是：

- 为 SDL 场景新增一个更适合手工验收的控件浏览 demo
- 用最小改动把现有 widget 控件拆成“逐页单控件展示”
- 为 `switch` 和其他控件提供统一的鼠标滑动浏览入口

---

## 2. 本轮目标

### 2.1 用户可见目标

交付后，SDL 侧需要新增一个独立 demo6，满足以下效果：

1. 通过 `USE_DEMO == 6` 可以单独启动新 demo
2. demo 启动后进入第 1 页，主控件为 `switch`
3. 用户必须通过鼠标水平拖动才能切换到上一页/下一页
4. 每页只展示 1 类主控件
5. 所有既定 widget 控件都能通过连续翻页访问到
6. 页面顶部固定显示控件名和页码
7. 左滑/右滑时切页动画与手势方向一致
8. 首页与尾页支持循环切换

### 2.2 工程目标

本轮实现需要满足以下工程边界：

- `demo2` 的源码、行为、布局、翻页方式全部不改
- 新 demo 的入口、页面、公共逻辑与 `demo2` 文件分离
- 优先只改 SDL demo 层和 widget demo 层，不修改底层 GUI 框架行为
- 如果确实需要触达底层输入相关 symbol，必须先做 GitNexus impact 分析，并将改动控制在最小范围

---

## 3. 非目标

本轮明确不做以下内容：

- 不重构现有 `demo2` 的四页 widget 结构
- 不把 `demo2` 自动轮播改成手动翻页
- 不实现通用的“任意 demo 可复用 gallery 容器”
- 不为每个控件补齐完整深交互验收脚本
- 不为了翻页手势去重写底层输入系统
- 不处理纵向翻页、双轴翻页、惯性滚动、速度判定
- 不做复杂的 page indicator、缩略图预览、分页目录
- 不把所有控件的拖动交互冲突彻底消除

本轮原则是：

> **先交付一个稳定、独立、可手工浏览全部控件的 demo6，再考虑通用化或更深交互。**

---

## 4. 总体方案

### 4.1 方案选型

本轮采用：

> **新增独立 `USE_DEMO == 6` + 新建一套单控件多页 gallery 文件。**

不采用以下思路：

- 在 `demo2` 里直接改页面行为  
  这会破坏“保持 `demo2` 不变”的要求
- 用单 page + 大量配置表一次性渲染全部控件  
  首轮实现复杂度偏高，不利于尽快稳定落地

### 4.2 整体结构

新 demo6 由三层组成：

1. **入口选择层**
   - 在 SDL 的 demo 选择逻辑中加入 `USE_DEMO == 6`
2. **gallery 公共层**
   - 负责页头、页码、提示文案、滑动判定、上一页/下一页跳转
3. **控件分页层**
   - 每个控件页只负责本页控件初始化和本页辅助文案

### 4.3 设计原则

- 页面的职责单一：每页只展示一个主控件类型
- 翻页逻辑集中：不要让每个 page 各自复制一套滑动判定
- 改动隔离：新 demo 尽量不依赖 `demo2` 的自动轮播逻辑
- 视觉清晰：主控件居中，四周留出足够空白，方便从空白区域发起翻页手势

## 5. 交互设计

### 5.1 翻页方式

新 demo6 只响应鼠标**水平拖动**切页：

- 按下时记录起点
- 移动或松开时计算位移
- 达到阈值后判定上一页或下一页
- 未达到阈值则留在当前页

翻页规则如下：

- `dx <= -threshold`：切到下一页
- `dx >= threshold`：切到上一页
- 其余情况：不翻页

### 5.2 手势判定约束

本轮使用简单、稳定的判定策略：

- 只支持水平滑动
- 不做速度判定
- 不做惯性
- 阈值建议固定为屏宽的约 `1/5`
  - 对 `480` 像素宽屏，可按 `90~100 px` 实现

这样做的目的：

- 避免轻微抖动导致误翻页
- 避免为了“跟手感”引入过多临界条件
- 让手工测试结果更稳定、可重复

### 5.3 翻页动画

切页动画继续复用现有 scene switching：

- 下一页：`ARM_2D_SCENE_SWITCH_MODE_SLIDE_LEFT`
- 上一页：`ARM_2D_SCENE_SWITCH_MODE_SLIDE_RIGHT`

原因：

- 与手势方向认知一致
- 不需要新建动画系统
- 与 SDL 现有 page jump 能力兼容

### 5.4 首尾循环

本轮首页和尾页采用循环切换：

- 第 1 页右滑：跳到最后一页
- 最后一页左滑：跳到第 1 页

这样做的优势：

- 控件巡检效率更高
- 不需要用户反复穿越整条链路返回首页

## 6. 控件交互与翻页冲突处理

### 6.1 基本取舍

新 demo6 的定位是：

> **控件浏览 + 基础交互验证优先，深度复杂交互次之。**

因此本轮不追求让所有“拖动型控件”和“页面滑动翻页”完全无冲突共存。

### 6.2 手势优先级

手势处理优先级定义如下：

- 普通点击 / 短按：优先交给控件
- 明显水平拖动：优先交给页面翻页

推荐判定流程：

1. 鼠标按下，记录 `startX` / `startY`
2. 鼠标移动时计算 `dx` / `dy`
3. 当 `|dx|` 明显大于 `|dy|` 且超过翻页阈值时，判定为“翻页手势”
4. 一旦本次手势被判定为翻页，则不再继续透传给控件
5. 若直到松手都未达到翻页条件，则维持普通点击/轻微移动语义

### 6.3 对控件交互的影响边界

这套规则下：

- `switch`、`button`、`checkbox` 之类点击型控件可正常体验
- `combo box`、`line edit` 可做基础验证
- `slider`、`scroll selecter`、`list`、`table` 等拖动型控件可能存在翻页竞争

因此本轮要求是：

- 点击型控件要能完成基础交互
- 拖动型控件允许以“展示 + 基础响应验证”为主
- 不要求在 demo6 中完整覆盖其所有复杂交互细节

### 6.4 页面布局辅助策略

为了降低冲突，每页布局应满足：

- 主控件居中
- 主控件四周留出足够空白
- 页头只显示信息，不放交互控件
- 页面底部可放一行静态提示文字，如 `Drag horizontally to change widget`

## 7. 控件分页顺序

本轮按控件类型重排，顺序固定如下：

### 7.1 第 1 组：开关与基础输入

1. `Switch`
2. `Button`
3. `CheckBox`
4. `LineEdit`
5. `ComboBox`

### 7.2 第 2 组：滑动与选择

6. `Slider`
7. `ScrollSelecter`
8. `List`
9. `Table`

### 7.3 第 3 组：文本与内容展示

10. `Label`
11. `Text`
12. `Image`
13. `Window`
14. `MessageBox`

### 7.4 第 4 组：状态与数据可视化

15. `ProgressBar`
16. `Gauge`
17. `Arc`
18. `Graph`

### 7.5 第 5 组：复合与高级控件

19. `DateTime`
20. `Calendar`
21. `QRCode`
22. `RadialMenu`
23. `IconSlider`

### 7.6 特殊说明

- `Switch` 固定为第 1 页
- `Keyboard` 不单独成页，作为 `LineEdit` 页的辅助能力存在
- `Window` 页可带一个嵌套 label，避免页面过空
- `MessageBox` 页直接展示 message box 结果，不走隐藏后弹出流程

## 8. 文件结构与改动边界

### 8.1 必须保持不变的现有文件行为

以下现有 widget demo 逻辑在本轮不能被改变：

- `examples/common/demo/widget/uiWidget.h`
- `examples/common/demo/widget/uiWidgetPage1.c`
- `examples/common/demo/widget/uiWidgetPage2.c`
- `examples/common/demo/widget/uiWidgetPage3.c`
- `examples/common/demo/widget/uiWidgetPage4.c`

允许修改的范围仅限于：

- SDL demo 选择入口增加新分支
- 新增 demo6 的独立文件
- 必要时增加极小的通用辅助函数

### 8.2 入口层改动

需要在以下位置新增 demo6 选择能力：

- `examples/sdl/user/ldConfig.h`
- `examples/sdl/CMakeLists.txt`

入口目标：

- 增加 `USE_DEMO == 6`
- 增加相应注释/帮助文案
- `LD_DEMO_GUI_INCLUDE` 指向新的 gallery 入口头文件
- `LD_DEMO_GUI_FUNC` 指向 gallery 首页 page func

### 8.3 新增文件建议

建议新增以下文件：

- `examples/common/demo/widget/uiWidgetSwipe.h`
- `examples/common/demo/widget/uiWidgetSwipe.c`
- `examples/common/demo/widget/uiWidgetSwipeCommon.h`
- `examples/common/demo/widget/uiWidgetSwipeCommon.c`

以及按页拆分的 page 文件，例如：

- `examples/common/demo/widget/uiWidgetSwipePage01.c`
- `examples/common/demo/widget/uiWidgetSwipePage02.c`
- `examples/common/demo/widget/uiWidgetSwipePage03.c`
- ...

如实现中更适合“每页一个 `.c` + 共享头文件”的形式，可以不保留 `uiWidgetSwipe.c`，但以下边界必须成立：

- 入口文件与公共逻辑文件独立
- demo6 的 page 文件命名与 `demo2` 文件明显区分
- 每个 page 文件职责只覆盖一个主控件页面

### 8.4 公共层职责

`uiWidgetSwipeCommon` 建议只负责：

- 统一页头绘制
- 页面索引、总页数、标题文案
- 鼠标滑动状态记录
- 上一页/下一页目标页决策
- 翻页动画模式选择

公共层不应负责：

- 每个控件的具体初始化细节
- 特定控件的复杂交互逻辑
- 底层输入系统改造

### 8.5 单页职责

每个 `uiWidgetSwipePageXX.c` 只负责：

- 创建背景和页头容器
- 创建本页主控件
- 创建少量辅助文案（控件名、提示、状态文字）
- 调用公共层提供的翻页能力

每页不应自行维护另一套独立翻页状态机。

## 9. 布局设计

### 9.1 页面基础布局

页面尺寸沿用当前 SDL widget demo 尺寸：

- `480 x 272`

建议统一布局元素：

- 顶部 header
- 中部主控件展示区
- 底部提示区

### 9.2 视觉布局原则

布局上应避免“信息太满”或“控件贴边”：

- 主控件在视觉上居中
- 控件与页边缘保留明显空白
- 页头左侧显示控件名
- 页头右侧显示 `current / total`
- 底部提示文字居中或靠左，风格尽量克制

### 9.3 单页附属信息

允许每页添加最少量辅助说明，例如：

- 当前控件名
- 交互提示
- 简单状态文本

但不应让单页演变成“控件说明文档页”。

## 10. 风险与兼容性

### 10.1 主要风险

1. **拖动型控件与滑动翻页竞争**
   - 风险：`slider`、`list` 等控件可能与翻页手势冲突
   - 策略：首轮接受“展示优先”，保持规则简单稳定

2. **为了拿到鼠标轨迹而下沉修改底层**
   - 风险：触达输入层后影响面变大
   - 策略：优先复用现有 SDL 输入能力；只有证据充分时才最小下沉

3. **demo6 文件数量偏多**
   - 风险：23 个控件页会带来较多 page 文件
   - 策略：接受“多文件换隔离清晰”的 tradeoff

### 10.2 兼容性要求

- `USE_DEMO == 2` 的构建和运行结果必须保持当前行为
- `USE_DEMO == 6` 的引入不能改变已有 demo 编译分支语义
- 新 demo 页面命名和符号命名应避免与 `uiWidgetPage1~4` 冲突

## 11. 验收标准

### 11.1 入口与隔离

验收时必须确认：

- `USE_DEMO == 2` 可正常构建运行，表现与当前一致
- `USE_DEMO == 6` 可单独构建运行
- `demo6` 与 `demo2` 的源码和行为互不污染

### 11.2 翻页行为

验收时必须确认：

- 水平拖动超过阈值时能稳定翻页
- 轻微位移或普通点击不会误触发翻页
- 左滑/右滑对应的动画方向正确
- 首页与尾页可循环切换

### 11.3 控件访问性

验收时必须确认：

- 第 1 页是 `switch`
- 所有既定控件页都可通过翻页访问
- 每页只包含 1 类主控件
- 页头可清楚显示控件名和页码

### 11.4 基础交互

验收时必须确认：

- `switch` 能正常切换
- 点击型控件可完成一次基本交互
- 拖动型控件至少能正确展示，且不会破坏整页翻页稳定性

---

## 12. 验证策略

### 12.1 构建验证

至少验证两组构建：

1. `USE_DEMO=2`
2. `USE_DEMO=6`

目的：

- 确认新入口不破坏旧 demo
- 确认新 demo 的 SDL 构建链路完整

### 12.2 运行验证

对 `demo6` 进行手工验证：

1. 启动后进入第 1 页 `switch`
2. 左滑进入下一页
3. 右滑返回上一页
4. 连续翻页直到尾页，再循环回首页
5. 抽查若干点击型控件是否可响应

### 12.3 回归验证

重新启动 `demo2`，确认：

- 仍然是当前的多页 widget demo
- 仍保持原本自动翻页/布局行为
- 不因为新 demo 的公共逻辑引入而产生异常

### 12.4 可测试逻辑建议

如果实现中把下列逻辑抽成独立小函数，建议补充单元测试：

- 翻页阈值判定
- 页索引前进/后退与循环
- 由拖动位移推导上一页/下一页决策

SDL 鼠标实际交互如难以自动化，可保留明确的手测步骤作为主验证链。

---

## 13. 实施建议

推荐实施顺序：

1. 先接入 `USE_DEMO == 6` 入口
2. 先做 3 页最小闭环：`Switch`、`Button`、`CheckBox`
3. 跑通滑动翻页与循环切换
4. 再按既定顺序扩展到全部控件页
5. 最后做 `demo2` 回归验证和文档补充

这样可以尽早确认最核心的“独立入口 + 滑动翻页”是否成立，避免一开始就把 23 页一次性堆满。
