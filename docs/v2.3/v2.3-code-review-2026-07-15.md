# TinyUI v2.3 代码评审与修复意见（2026-07-15）

## 结论

当前 v2.3 **不得声明完成或可发布**。本次评审确认 2 个此前门禁未覆盖的实现级 P1，以及 3 个已由 release evidence 证实的发布阻断项。现有 focused layout/theme、backend mapping 和 visible UI 测试通过，不能覆盖下列缺口。

## 范围与方法

- 基线：`docs/v2.3/2026-07-13-tinyui-v2-3-unified-core-design.md`、`v2.3-capability-evidence-matrix.md`、`v2.3-release-gates.md`。
- 代码：TinyUI runtime、window、flex/grid、theme 和对应 unit/contract/runtime 测试。
- 证据：`build/v2.3/release-evidence/*.json` 与本次复跑结果。
- GitNexus：本环境未索引 `LingDongGUI`，无法生成图谱级 impact/detect_changes 结果；该限制本身保持为发布阻断，不以 `rg` 结果替代正式影响分析。

## Findings

### P1-001：layout/theme 首次调用会隐式堆分配，且 OOM 仍可能返回成功

**状态：已修复（本次）**。

**位置：** `tinyui/src/widgets/window.c:330-390`，经 `tinyui/src/layout/flex.c:142-218`、`tinyui/src/layout/grid.c:88-205` 和 `tinyui/src/core/widget.c:372-392` 进入。

**问题：** `tinyui_window_sync_padding()` 在 `padding_group_storage` 为空时无条件调用 `ldCalloc()`（第 366-368 行），即使当前不需要 padding group 也会分配。flex/grid setter 和窗口 padding setter 忽略该分配结果并返回 `TINYUI_OK`。当 `has_explicit_flex_padding` 为真且分配失败时，第 380-387 行会把未初始化的局部 `padding_group` 用于 native setter，并把空指针交给 `ldWindowSetPaddingGroup()`。

**违反基线：** 设计要求 layout、theme apply 不得分配 heap，OOM 必须返回明确错误（统一设计 `6.3`）；release manifest 也将 `layout_implicit_heap_bytes=0`、`theme_apply_implicit_heap_bytes=0` 固定为门禁阈值。

**影响：** 首次 `tinyui_flex_set_*()`、`tinyui_grid_set_*()`、`tinyui_obj_set_padding()`，以及 window/background 上带 `TINYUI_STYLE_PADDING` 的 `tinyui_obj_apply_style()` 都可能引入未计入当前测试的隐式分配。在受限 MCU 上，这既破坏零分配契约，也把 native 配置失败伪装成成功。

**修复建议：**

1. 删除惰性堆分配。将长期存活的 `ldPadding_t` 直接嵌入 `struct tinyui_window`，让 `ldWindowSetPaddingGroup()` 指向该嵌入字段；同时删除 `padding_group_storage` 的 `ldCalloc/ldFree`。
2. 将 `tinyui_window_sync_padding()` 改为返回状态，并使 flex/grid/padding/theme 调用链在 native 同步失败时返回 `TINYUI_ERROR_BACKEND`；状态更新应在 native 成功后提交，避免半更新。
3. 在改动前对受影响函数执行 GitNexus upstream impact。索引恢复后，`tinyui_window_sync_padding`、`tinyui_flex_set_*`、`tinyui_grid_set_*` 的风险需要按直接调用者和执行流复核。

**必须补测：**

- allocator 计数测试：新建 window 后 reset 计数，首次分别调用 `tinyui_flex_set_flow()`、`tinyui_grid_set_columns()`、`tinyui_obj_set_padding()`，以及对 window 应用 `TINYUI_STYLE_PADDING`；每一步 heap delta 必须为 0。
- allocator fail injection：若保留任何需要分配的 native storage，强制失败后 API 必须返回错误，且 LingDongGUI padding/布局状态不变。
- 继续运行 wrapper ABI gate，确认嵌入字段没有突破 `5%/8 B` 与绝对尺寸门槛。

**验证：**

```sh
rtk cmake --build build/v2.3 -j8
rtk ctest --test-dir build/v2.3 -R '^(test_tinyui_theme|test_tinyui_layout|test_tinyui_v23_layout_resource_contract|test_tinyui_steady_state_allocation|test_tinyui_wrapper_struct_overhead)$' --output-on-failure
rtk ctest --test-dir build/v2.3 -R '^(check_tinyui_visible_ui_v23_theme_layout_resource|check_tinyui_backend_mapping_v23_theme_layout_resource)$' --output-on-failure
```

已执行：新增的 window `TINYUI_STYLE_PADDING` allocator 红测先失败，修复后 `test_tinyui_theme`、`test_tinyui_layout`、wrapper/pool/descriptor ABI gate 均通过。

### P1-002：release 聚合器接受必需 artifact 的 `status=fail`，存在假绿风险

**状态：已修复（本次）**。

**位置：** `tests/tinyui/contract/check_tinyui_v23_release_gates.py:452-511,537-567`。

**问题：** `validate_artifact_payload()` 只拒绝 `fallback=true` 和 `status=pending`，并未拒绝 `status=fail`；`validate_artifacts()` 对所有 `required_for_closeout=true` artifact 也只调用这段校验。当前 `standard.json`、`asan.json`、`ubsan.json`、`manual_review.json` 都是 `status=fail`，但聚合器实际只报告 GitNexus fallback。一旦把 GitNexus artifact 改为 `fallback=false`，聚合器可能在 sanitizer、人工评审和标准 profile 仍失败时错误返回成功。

**违反基线：** release gate 的 fail-closed 原则要求失败门禁绝不能写成通过，G1/G4/G5/G6 也要求对应 artifact 完全通过。

**修复建议：**

1. 对 `required_for_closeout=true` 的 artifact 强制 `status == "pass"`；`fail`、`pending`、未知值和 `fallback=true` 均产生聚合错误。
2. 保留 `port_completed=false` 作为允许的延迟事实，但将 `manual_reviewed_passed=false` 明确转化为聚合失败，不能只保存在 JSON 内。
3. 为 standard、ASan、UBSan、manual review 分别新增 checker unit test，断言 `status=fail` 时聚合器失败；同时覆盖未知 status 和 `fallback=true`。

**验证：**

```sh
rtk python3 tests/tinyui/contract/check_tinyui_v23_release_gates.py \
  --build-dir build/v2.3 \
  --manifest tests/tinyui/contract/tinyui_v23_release_gate_manifest.json \
  --artifact-root build/v2.3/release-evidence
rtk ctest --test-dir build/v2.3 -R '^test_check_tinyui_v23_release_gates$' --output-on-failure
```

期望：当前四个 `status=fail` artifact 分别产生错误；只有全部 required artifact 为 `status=pass` 且没有 fallback 时才允许聚合通过。

已执行：新增 Python 红测先证明 `standard`、`asan`、`manual_review` 的 `status=fail` 和未知 status 会被放行；修复后 11/11 unit 通过，当前聚合器实际报告 7 个 required artifact/fallback 阻断项。

### P1-003：GitNexus artifact 为 fallback，最终聚合门禁 fail-closed

**状态：索引已恢复，release artifact 待在无关工作区变更隔离后重新生成**。

**位置：** `build/v2.3/release-evidence/gitnexus-impact.json:5-9`，`tests/tinyui/contract/tinyui_v23_release_gate_manifest.json:106-110`。

**问题：** 证据文件为 `status=fail`、`fallback=true`，而 manifest 将其列为 closeout 必需 artifact。当前聚合器实际报 `artifact_fallback_true | artifact=gitnexus`。

**修复建议：** 在可用 GitNexus 环境重新索引仓库后，对 `master` 执行 `detect_changes(scope="compare", base_ref="master")`，并对本次 P1 涉及符号执行 upstream impact。仅在新的 artifact 为 `fallback=false` 且高风险调用者已有迁移/测试清单时，才可更新 release evidence。

**验证：**

```sh
rtk python3 tests/tinyui/contract/check_tinyui_v23_release_gates.py \
  --build-dir build/v2.3 \
  --manifest tests/tinyui/contract/tinyui_v23_release_gate_manifest.json \
  --artifact-root build/v2.3/release-evidence
```

期望：`total_errors=0`，且 `gitnexus-impact.json` 的 `fallback=false`。

### P1-004：84 项可操作能力仍使用家族级 partial L5-E 证据

**位置：** `build/v2.3/release-evidence/manual_review.json:5-29`，`docs/v2.3/v2.3-capability-evidence-matrix.md` 中标注 `L5-E partial` 的控件行。

**问题：** 人工评审明确记录 `manual_reviewed_passed=false`、`l5e_partial_family_rows=84`，因此“所有 required 可操作能力达到 L5-E”的 release 条件并未满足。矩阵 checker 通过仅代表行与工件引用格式有效，不代表每项用户操作均有独立真实事件证据。

**修复建议：** 为 calendar、combo_box、icon_slider、line_edit、radial_menu、scroll_selector、table 等复杂交互控件按 `capability_id` 增加真实 LingDongGUI 输入、callback trace 与最终 native 状态断言。禁止用同家族代表场景覆盖未执行的 setter 或事件分支。

**验证：**

```sh
rtk python3 tests/tinyui/contract/check_tinyui_release_capability_matrix.py
rtk ctest --test-dir build/v2.3 -R '^(check_tinyui_event_evidence|check_tinyui_backend_mapping)$' --output-on-failure
```

期望：更新后的人工记录为 `manual_reviewed_passed=true`，并可逐条定位 L5-E trace。

### P1-005：ASan/UBSan 当前不是零失败，不能作为已关闭残余

**状态：部分修复（本次）**。`src/gui/ldBase.c` 的 Freertos heap4 backing storage 已从 4 字节改为 8 字节对齐，并新增 `test_tinyui_button_events` 回归断言；该测试在标准与 UBSan profile 均通过，不再触发 `freeRtosHeap4.c:396` 的未对齐写入。完整 sanitizer 仍未清零。

**位置：** `build/v2.3/release-evidence/asan.json`、`build/v2.3/release-evidence/ubsan.json`。

**问题：** ASan 记录 120 项中 28 项失败及 Arm-2D global-buffer-overflow；UBSan 记录 57 项失败/未完成，并包含 `ldSwitch`、`ldWindow`、`ldBase` 空指针偏移和 `freeRtosHeap4` 未对齐写入。它们直接违反 G5/G6 的零失败、零 sanitizer 报告要求。

**修复建议：** 将 sanitizer 清零作为独立根因修复工作，而不是在 TinyUI release gate 中排除。每个失败先归类为 TinyUI、LingDongGUI、Arm-2D 或测试宿主；对于确属第三方/host 的项，需有最小复现、责任边界和经人工批准的排除记录，不能只用通配 label 隐藏失败。

**验证：** 使用 G5/G6 指定的 Clang CMake profile clean configure、build 和完整 CTest；证据中 `core_sanitizer_clean=true`、失败数为 0，且没有未解释 exclusion。
