# PicoUI a-0.6 控件能力 1 对 1 对比审计

> 历史说明：本文是 `a-0.6` 阶段审计结论，保留当时“release contract 子集而非 native-100”口径。当前主仓若讨论 `a-0.7`，以 `tests/picoui/contract/picoui_native_100_inventory.json`、`tests/picoui/contract/picoui_release_capability_matrix.json` 和 `docs/picoui-serial/a-0.7-线计划索引.md` 为准。

## 审计结论

本审计基于当前主仓代码、`a-0.6` release matrix、runtime/mapping/visible gate 和 LingDongGUI `src/gui/ld*.h` 公开能力复核。

结论分三层：

1. 控件数量覆盖：`PicoUI` 已覆盖当前 release matrix 定义的 `26/26` 个 LingDongGUI 可封装控件。
2. Release contract 覆盖：`PicoUI` 的 `a-0.6` contract 已把 26 个控件全部收敛到 `final_release_ready`，但其中包含 `13` 条 `reject-with-rationale` 能力边界。
3. LingDongGUI 原生能力 100% 覆盖：未达到。原因是 `PicoUI` 仍没有公开若干 LingDongGUI 原生高级能力；这些能力被当前 release contract 明确 reject，而不是实现覆盖。

因此，不能把 `a-0.6 final release ready` 写成“PicoUI 已 100% 镜像 LingDongGUI 全部原生控件能力”。更准确口径是：

`PicoUI a-0.6` 已完成 26 个 release-target 控件的 public API、真实 backend 映射和发布合同闭环；但它是一个经过裁剪的上层 API 合同，不是 LingDongGUI 原生 API 的 100% 镜像。

## 审计依据

关键证据：

1. LingDongGUI widget 枚举包含 `widgetTypeWindow` 到 `widgetTypeClock`，并包含 `widgetTypeAnimation`：`src/gui/ldBase.h:36`。
2. PicoUI public umbrella header 纳入 26 个控件 header，未纳入 animation：`picoui/include/picoui/picoui.h:4`。
3. `a-0.6` release matrix 记录 `ldgui_wrappable_widget_total = 26`、`picoui_wrapped_widget_total = 26`、`full_parity_complete_total = 26`，同时记录 `capability_status_counts.reject = 13`：`tests/picoui/contract/picoui_release_capability_matrix.json:49`。
4. release matrix gate 固定 26 个 expected wrapped widgets，`EXPECTED_NOT_WRAPPED_WIDGETS = set()`：`tests/picoui/contract/check_picoui_release_capability_matrix.py:10`。
5. backend mapping gate 覆盖 22 个 formal mapping demo，`message_box` 明确走 formal mapping exclusion：`tests/picoui/runtime/check_picoui_backend_mapping.py:165`、`tests/picoui/runtime/check_picoui_backend_mapping.py:248`。
6. backend runtime 仍保留 `temporary smoke path` 和 opt-in smoke cursor layout：`picoui/src/backend/ldgui/backend_app.c:157`、`picoui/src/backend/ldgui/backend_app.c:590`。
7. `a-0.6` closeout 自身也声明 manual artifact 不等于 live OS 窗口现场人工验收：`docs/picoui-serial/a-0.6-final-release-closeout.md:120`。

## 控件数量对齐

LingDongGUI `ldBase` 枚举中有 27 个 widget-like 类型：

`window / button / image / text / line_edit / graph / checkbox / slider / switch / progress_bar / gauge / qrcode / date_time / icon_slider / combo_box / arc / radial_menu / scroll_selecter / label / table / keyboard / animation / list / message_box / calendar / progress_wheel / clock`

PicoUI `a-0.6` release target 覆盖其中 26 个，未纳入 `animation`。

`ldAnimation` 有 widget 生命周期和 `ldAnimation_init()`，但当前历史文档把它定位为更接近动画辅助组件，未作为 `a-0.6` release-target 控件。因此：

1. 按当前 release-target 定义：26/26 覆盖成立。
2. 按 LingDongGUI 全部 widget-like 类型定义：26/27 覆盖，`ldAnimation` 未覆盖。

## 能力缺口分类

### 明确 reject 的能力

当前 release matrix 内已有 `13` 条 reject：

1. `image.theme`
2. `image.bg_text_border_radius_colors`
3. `image.padding`
4. `image.enabled`
5. `list.item_marker`
6. `progress_bar.advanced_skin_and_theme`
7. `qrcode.advanced_qrcode_configuration`
8. `progress_wheel.advanced_animation_and_theme`
9. `message_box.multi_button_and_modal_behavior`
10. `date_time.advanced_datetime_modes`
11. `clock.advanced_clock_configuration`
12. `line_edit.editing_and_finished_boundary_without_reason`
13. `line_edit.submit_cancel_reason`

这些 reject 是合理边界时，可以支撑 `PicoUI release contract ready`；但它们不能支撑“能力 100% 覆盖”。

### 未进入 matrix 的原生高级能力

除 reject 外，LingDongGUI 还存在大量原生能力未逐项写入 PicoUI public contract，例如：

1. `ldAnimation` 整体组件。
2. 多控件图片/mask 资源高级配置。
3. 多控件完整颜色、字体、对齐、透明、背景图、skin/theme 组合。
4. `ldTable` 单元格图片/按钮/Excel type/align grid/navigation。
5. `ldGraph` axis/grid/frame/point mask。
6. `ldClock` 表盘和三指针资源配置。
7. `ldQRCode` ECC/maxVersion/zoom/color。
8. `ldKeyboard` key map、user draw、target btn list。
9. `ldBase` 通用 opacity/select/corner/center/flex min/max 等底层能力的全量 public readback。

这些能力并不一定都应该进入 PicoUI，因为 PicoUI 是上层 API，不是第二套 `ld*` API 镜像。但如果目标定义为“所有控件对应的能力 100% 覆盖”，就必须把它们纳入后续 contract。

## Gate 覆盖边界

当前 gate 证明强度如下：

1. contract gate：证明矩阵结构、26 控件行、summary 计数、若干关键 capability 行和 manual artifact 字段。
2. backend mapping gate：证明多数 demo 的 named widget 进入真实 LingDongGUI backend object；不证明每个原生 setter/getter 都映射。
3. visible gate：证明 demo 可见性和部分像素/结构 heuristic；不证明每个控件全部视觉能力。
4. runtime gate：证明 demo 能启动和 runtime marker；不是逐控件全能力验证。
5. manual artifact：当前是 artifact-based visual observation；不等于 live OS 窗口现场人工验收。

因此，当前 gate 能支撑 `a-0.6 release contract ready`，不能单独支撑“所有 LingDongGUI 原生能力 100% 覆盖”。

## 文档口径修正建议

建议后续所有 release 文档使用下面口径：

1. 可以写：`PicoUI a-0.6 已覆盖 26/26 release-target 控件，并完成 final release contract。`
2. 可以写：`PicoUI a-0.6 的 26 个控件均有 public API、backend 映射、unit/contract/gate 证据，特殊控件保留 special-case 边界。`
3. 不应写：`PicoUI 已 100% 覆盖 LingDongGUI 全部控件能力。`
4. 不应写：`PicoUI 已完整镜像所有 ld* setter/getter、事件、视觉、theme、skin、资源配置能力。`

若后续确实要追求“LingDongGUI 原生能力 100% 覆盖”，建议新开 `a-0.7` 或 `v1.0-hardening` 线，先把 `ldAnimation` 是否纳入控件范围、13 条 reject 是否转 support、以及所有未入 matrix 的高级能力是否进入 public API 合同逐项冻结。
