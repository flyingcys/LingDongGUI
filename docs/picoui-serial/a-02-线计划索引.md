- 并行拓扑说明：本文只定义 `a-02` worktree 的长期职责、写面边界和合并节奏；不替代 `H线/J线` 作为发布真相源。

- 当前新控件 vertical-slice 历史参考：`docs/picoui-serial/F-线计划索引.md`

## a-02 线定位

`a-02` 线负责低耦合新控件 vertical slice，用最少 shared 改动换取最快覆盖率提升。

当前只做以下候选：

1. `progress_bar`
2. `qrcode`
3. `progress_wheel`
4. `message_box`
5. `date_time`
6. `clock`

其中：

- `progress_bar` 是第一优先级。
- `qrcode` 是第二优先级。
- `progress_wheel` 是第三优先级。
- `message_box / date_time / clock` 属于第二批。

## 当前明确不做

1. 不做 `line_edit`
2. 不做 `combo_box`
3. 不做 `keyboard`
4. 不做 `table`
5. 不做 `graph`
6. 不做 `calendar`
7. 不做 `scroll selecter`
8. 不做高耦合输入/focus/dropdown/data-model 合同

原因：

- 这些方向会明显提高 shared event、focus、selectable、input model 冲突概率。
- 当前目标是减少与 `a-01` 线的互相干扰，不是一次吃掉所有高价值控件。

## worktree

- 目录：`.worktree/a-02`
- 建议分支：`feat/picoui-a-02-new-widgets`

创建或切换后必须执行：

```bash
git submodule sync --recursive
git submodule update --init --recursive
```

## a-02 线做什么

1. 逐个串行实现低耦合新控件 vertical slice。
2. 每个控件都同步 public API、widget、backend、demo、unit、runtime/mapping/visible gate。
3. 尽量把修改局限在各控件私有文件和 demo/test 接入层。
4. 在最少 shared 改动前提下提升控件覆盖率。
5. 把 `a-02` 第一轮覆盖目标从 `+3` 提升到 `+6`，但仍保持低耦合属性。

## a-02 线不做什么

1. 不争抢 `a-01` 持有的 shared-owner 文件。
2. 不顺手修 backlog 控件的共享合同问题。
3. 不把新控件 demo 通过写成整条 PicoUI 发布能力完成。
4. 不在一个阶段内并行推进两个新控件。
5. 不把 `a-02` 扩成“剩余未覆盖控件全吞线”。

## 串行顺序

固定顺序：

1. `a-02-B1 progress_bar`
2. `a-02-B2 qrcode`
3. `a-02-B3 progress_wheel`
4. `a-02-B4 message_box`
5. `a-02-B5 date_time`
6. `a-02-B6 clock`

顺序原因：

- `progress_bar` 与当前已有 `slider/image skin` 经验相邻，但输入耦合低，最适合先起量。
- `qrcode` 是显示型控件，交互轻，适合作为第二个低冲突切片。
- `progress_wheel` 仍属进度类，和 `progress_bar` 邻近，适合作为第三个低冲突切片。
- `message_box` 带复合结构和 callback，复杂度高于前三者，放入第二批起点。
- `date_time` 是轻量文本显示变体，复杂度可控。
- `clock` 是显示型控件，但包含指针/图片语义，放在第二批末尾。

若某个新控件在阶段末尾必须接入共享层，规则是：

1. 先把该控件私有文件全部收口。
2. rebase 到 `a-01` 最近 checkpoint。
3. 只做一次最小 shared 接入。
4. 接入后立刻跑 targeted 验证并准备回灌。

## 与 01 线的隔离规则

1. `a-02` 不修 `image/text/checkbox/switch/list` backlog。
2. `a-02` 不修改 release matrix 口径。
3. `a-02` 若发现 shared 语义缺口，记录到阶段文档或 review，优先由 `a-01` 吸收。
4. `a-02` 的目标是“新控件切片完成”，不是“顺手统一整理 PicoUI shared core”。
5. `a-02` 当前只扩到低耦合 `6` 控件，不上升到输入/数据模型总线。

## 每阶段最小验收

每个 `a-02-Bx` 阶段结束至少执行：

```bash
rtk cmake -S . -B build -DUSE_DEMO=0
rtk cmake --build build
python3 tests/picoui/contract/check_picoui_public_api.py
python3 tests/picoui/contract/check_picoui_demo_boundary.py
git diff --check
```

若该阶段已接入 demo/runtime，再追加：

```bash
python3 tests/picoui/runtime/check_picoui_runtime.py
python3 tests/picoui/runtime/check_picoui_backend_mapping.py
python3 tests/picoui/runtime/check_picoui_visible_ui.py --demo <demo_name>
```

若已新增 unit target，再追加：

```bash
ctest --test-dir build -R <test_target> --output-on-failure
```

注意：

- `a-02` 使用自己 worktree 下独立 `build` 目录。
- 不要与 `a-01` 共用任何 build 产物。
- `a-02` 内部也不要并行跑 runtime / visible / mapping。

## merge-back 节奏

推荐按控件单独回灌：

1. `progress_bar`
2. `qrcode`
3. `progress_wheel`
4. `message_box`
5. `date_time`
6. `clock`

只有当前一控件已经 merge-back 或明确冻结，才进入下一控件的 shared 接入阶段。

每次回灌前主线程至少检查：

```bash
git status --short --branch --ignore-submodules=all
git diff --stat
git diff --check
```

## 当前正确口径

- `a-02` 线是“低耦合新控件扩面线”，不是 shared contract 主线。
- `a-02` 线的成功标准是单控件 vertical slice 真正闭环，而不是一次扩很多控件名义覆盖。
- `a-02` 线必须优先保护与 `a-01` 线的边界清晰，避免把多 worktree 加速变成多 worktree 互撞。
- 当前扩展版 `a-02` 做完后，PicoUI 预计从 `9 / 26` 提升到 `15 / 26`，数量覆盖率约 `57.7%`；这仍不是 LingDongGUI 全控件覆盖。
