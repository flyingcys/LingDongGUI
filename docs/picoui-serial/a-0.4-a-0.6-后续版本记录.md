# PicoUI a-0.4 到 a-0.6 后续版本记录

## 目的

这份文件只做一件事：

把 `a-0.4 / a-0.5 / a-0.6` 怎么干先记录下来，防止 `a-0.3` 做完以后路线断掉。

当前边界：

1. 这里只记录后续版本定义。
2. 这里只冻结版本目标、控件范围、shared 依赖、完成定义。
3. 这里不展开成后续详细 spec。
4. 这里不展开成后续详细 plan。

当前已补充的细化入口：

1. `a-0.4` 设计 spec：`docs/superpowers/specs/2026-05-31-picoui-a-0-4-input-shared-core-design.md`
2. `a-0.5` 设计 spec：`docs/superpowers/specs/2026-05-31-picoui-a-0-5-data-model-design.md`
3. `a-0.4` 串行索引：`docs/picoui-serial/a-0.4-线计划索引.md`
4. `a-0.5` 串行索引：`docs/picoui-serial/a-0.5-线计划索引.md`
5. `a-0.6` 设计 spec：`docs/superpowers/specs/2026-06-01-picoui-a-0-6-full-release-design.md`
6. `a-0.6` 执行 plan：`docs/superpowers/plans/2026-06-01-picoui-a-0-6-full-release-implementation.md`
7. `a-0.6` final closeout：`docs/picoui-serial/a-0.6-final-release-closeout.md`

## 最终总目标

最终总目标不变：

1. PicoUI 覆盖 LingDongGUI 当前 `26` 个可封装控件。
2. PicoUI 每个控件与对应 `ld*` 控件完整功能对齐。
3. 最终不接受 `wrapped`、`stable contract`、`minimal vertical slice` 作为完成口径。

## a-0.4 输入与选择 shared-core 版

### 目标

建立 PicoUI 后续高耦合输入控件所需的 shared-core。

当前冻结为严格串行版，不再接受四控件平推。

### 主攻控件

1. `line_edit`
2. `keyboard`
3. `combo_box`
4. `scroll_selecter`

### 关键 shared 依赖

1. focus ownership
2. editable text contract
3. keyboard bridge
4. selection / navigation contract
5. dropdown contract

进入控件实现前，必须先处理：

1. runtime/layout honesty
2. getter truth policy

### 完成定义

`a-0.4` 完成时至少要满足：

1. 上述 `4` 个控件进入 PicoUI public widget 集。
2. 输入/选择 shared-core 不再靠局部 demo 逻辑支撑。
3. `line_edit / keyboard / combo_box / scroll_selecter` 都有真实 backend mapping。
4. unit / contract / mapping / visible 证据齐全。
5. current matrix 与文档同步更新。

当前 `a-0.4` 实际状态：

1. `line_edit / keyboard / combo_box / scroll_selecter` 已全部进入 PicoUI public widget 集。
2. shared-core 的 `honesty / focus / selection truth / dropdown / edit-mode` 已按 `R0-R6` 串行落地。
3. `line_edit / combo_box / scroll_selecter` 已进入 visible gate；`keyboard` 已进入 runtime gate。
4. `R7` 的主任务是把 matrix / gate / 中文文档与当前代码态收口一致，不再把 `keyboard / combo_box / scroll_selecter` 记为 `not_wrapped`。
5. 这不等于四个控件已经 `full_parity_complete`；release matrix 当前仍把它们收敛为 `stable_contract_but_not_full_parity`。
6. 当前 review 已完成两处关键收口：
   - `keyboard` 的 matrix evidence layer 已回调为 runtime-first，不再写成独立 mapping / visible 已 present
   - `scroll_selecter` 的 backend `kind` / shared data-model metadata 已修正到 `PICOUI_BACKEND_WIDGET_SCROLL_SELECTER`

### 主要风险

1. `line_edit` 与 `keyboard` 会互相卡住。
2. `combo_box` 与 `scroll_selecter` 会碰 shared selectable/navigation 语义。
3. 若这版只接 API 名字、不做 shared-core，后面 `table` 一定返工。

### 严格顺序

1. `honesty + readback policy`
2. `focus ownership`
3. `line_edit`
4. `keyboard`
5. `selection / navigation contract`
6. `combo_box`
7. `scroll_selecter`

## a-0.5 数据 / 时间 / 表格版

### 目标

建立 PicoUI 后续数据模型类控件所需的 shared model。

当前冻结为 shared-model first 版，不再接受三控件平推。

### 主攻控件

1. `table`
2. `graph`
3. `calendar`

### 关键 shared 依赖

1. item model
2. editable cell contract
3. graph series model
4. calendar date/grid contract
5. 与 `a-0.4` 输入 shared-core 的联动

进入 `graph / calendar` 前，必须先由 `table` 验证：

1. item model 真实成立
2. editable cell contract 真实成立

### 完成定义

`a-0.5` 完成时至少要满足：

1. `table / graph / calendar` 进入 PicoUI public widget 集。
2. `table` 的 item/edit model 不是 demo 假逻辑。
3. `graph` 的 series/value 合同真实落到底层。
4. `calendar` 的 date/header/grid 合同真实落到底层。
5. matrix、文档、gate 同步收口。

当前 `a-0.5` 实际状态：

1. `table / graph / calendar` 已全部进入 PicoUI public widget 集。
2. `table` 已用真实 `ldTable` 证明 item model 与 editable-cell commit boundary 复用 shared-core，但当前不把 cancel/abort reason 写成已稳定 public contract。
3. `graph` 已用真实 `ldGraph` 证明 series/value/readback 合同。
4. `calendar` 已用真实 `ldCalendar` 证明 date/header/grid/readback 合同。
5. `R5` 的主任务是把 matrix / gate / 中文文档与当前代码态收口一致，不再把 `table / graph / calendar` 记为 `not_wrapped`。
6. 这同样不等于三控件已经 `full_parity_complete`；release matrix 当前仍把它们收敛为 `stable_contract_but_not_full_parity`。

### 主要风险

1. `table` 最容易扩散到 keyboard/edit/focus。
2. `graph` 若只做静态画图，后面还会返工。
3. `calendar` 若只做显示不做真实 date contract，也是假完成。

### 严格顺序

1. `item model`
2. `editable cell contract`
3. `table`
4. `graph`
5. `calendar`

## a-0.6 全量发布缺口总账版

### 目标

把 PicoUI 收口到“可发布的全量 LingDongGUI 控件 + 功能对齐版本”。

这里不再把 `a-0.6` 理解成“只补最后 4 个未包裹控件”。真实目标是：

1. 补齐最后 `4` 个 `not_wrapped` 控件。
2. 把当前 `12` 个 `stable_contract_but_not_full_parity` 控件收口到 `full_parity_complete`。
3. 把当前 `6` 个 `minimal_vertical_slice_only` 控件从纵切片收口到完整发布合同。
4. 把当前仍然按 `a-0.3 current-15` 口径记录的 matrix / gate / 中文文档，升级成真正服务最终发布的 truth-source。

### 当前真实基线

截至当前主仓，机器真相源已经升级到 `a-0.6 final release` 口径，当前基线是：

1. `ldgui_wrappable_widget_total = 26`
2. `picoui_wrapped_widget_total = 26`
3. `picoui_not_wrapped_widget_total = 0`
4. `full_parity_complete_total = 26`
5. `stable_contract_but_not_full_parity_total = 0`
6. `minimal_vertical_slice_only_total = 0`

这说明 `W1/W2/W3/W4-A` 的代码、matrix、gate catalog 主线已经推进到 final release 口径；当前未闭环的重点已转成：

1. demo-level manual artifact 已覆盖 final release 目标集，但当前仍停留在 artifact-based visual observation，不等于 live OS 窗口现场验收通过
2. 中文发布文档与 closeout 文档仍在继续收口
3. 最终 requirement-by-requirement 完成审计还未结束

#### W4. 证据层升级

3. widget-level capability audit
4. runtime / mapping / visible / manual artifact 全量一致性
5. 中文发布文档与 closeout 文档收口

### 关键 shared 依赖

1. theme / style / metadata 语义边界
2. getter/readback honesty 与 backend truth
3. input/edit/select/data-model shared-core 的最终公共合同
4. multi-part visual contract
5. angle / pointer / progress contract
6. composite navigation contract
7. animation / visible evidence boundary
8. release truth-source schema 升级

### 当前方向修正

旧方向的问题是：把 `a-0.6` 写成“补 4 个复合视觉控件，并做最终审计”。

这个方向不够，因为：

1. 它只能解决 `26/26 wrapped`，不能解决 `26/26 full parity complete`。
2. 它默认 `a-0.4 / a-0.5 / a-02 / a-01` 已包裹控件只需审计，不需整改；这与当前 matrix 不符。
3. 它会把“审计”写成纸面动作，而不是把 `stable/minimal` 真实收口成 `full parity` 的整改动作。

因此从本次起，`a-0.6` 的主定义改为：

1. `全量发布缺口总账`
2. `4 个未包裹控件实现`
3. `18 个已包裹但未 full parity 控件整改`
4. `最终发布 truth-source / gate / docs 升级`

### 控件级发布缺口总账

#### A. 已 full parity，可视为最终发布基线

1. `window`
2. `label`
3. `button`
4. `slider`

这 `4` 个当前仍是唯一能维持 `full_parity_complete` 口径的控件。

#### B. `stable contract but not full parity`，必须继续整改

1. `checkbox`
   - 还差更完整状态/样式 readback。
   - 不能把 radio group、image mode、组合排版、导航语义写成已完成。
2. `switch`
   - 还差 direction/navigation、track/knob image skin 等更高阶能力。
   - 当前公开 readback 仍主要只有 `checked`。
3. `text`
   - 还差更完整 public readback。
   - 复杂文本模型、字体资源、scroll/seek/background image 仍未形成发布合同。
4. `image`
   - `theme` 明确仍是 `reject`。
   - `style_class/user_data` 仍是 metadata-only `incomplete_contract`。
   - `enabled` 仍是 `reject`。
   - 颜色/圆角/padding 不能写成 image 已支持样式能力。
5. `list`
   - `item_marker` 明确仍是 `reject`。
   - `style_class` 与 widget-level `user_data` 仍是 metadata-only `incomplete_contract`。
   - callback cookie 分离不等于 list 全面 parity。
6. `line_edit`
   - `editing_and_finished_boundary_without_reason` 仍是 `deferred`。
   - `submit_cancel_reason` 仍是 `deferred`。
7. `keyboard`
   - 当前只稳定证明 bridge/ownership runtime 路径。
   - 仍未形成 dedicated mapping/visible gate 覆盖闭环。
   - 不能把 runtime-first 证据偷换成 full parity。
8. `combo_box`
   - 当前只稳定证明 dropdown truth 与 real mapping。
   - 仍未证明完整 theme/visual parity。
9. `scroll_selecter`
   - 当前只稳定证明 selected-item truth 与 edit-mode boundary。
   - 仍未证明完整 visual/theme parity。
10. `graph`
   - 当前只稳定证明 series/value/readback truth。
   - 仍未证明 advanced chart feature/theme parity。
11. `table`
   - 当前只稳定证明 item model 与 editable-cell commit boundary。
   - richer cancel/abort public contract 仍缺。
   - 不能把当前 table 写成 full feature parity。
12. `calendar`
   - 当前只稳定证明 date/header/grid truth。
   - 仍未证明完整 calendar feature/theme parity。

#### C. `minimal vertical slice only`，必须从纵切片升级为发布合同

1. `progress_bar`
   - 当前只证明 `percent/horizontal`。
   - advanced skin/theme、更多尺寸/配色/public contract 仍缺。
2. `qrcode`
   - 当前只证明文本输入与 readback。
   - 纠错等级、缩放、边距、前景/背景色、尺寸等仍未暴露。
3. `progress_wheel`
   - 当前只证明 `percent`。
   - 动画、主题、尺寸、配色仍缺。
4. `message_box`
   - 当前只证明单确认按钮竖切片。
   - 多按钮、取消路径、返回值模型、模态控制、布局定制仍缺。
   - getter 还是 host cache，不是 backend readback。
5. `date_time`
   - 当前只证明 format 可读回，date/time 可写入。
   - 日期时间 public readback、复杂模式、locale、时区、自动同步策略仍缺。
6. `clock`
   - 当前只证明 `step_second`。
   - 表盘资源、时间源、指针/刻度配置、复杂动画仍缺。

#### D. `not_wrapped`，仍未进入 public widget 集

1. `arc`
2. `gauge`
3. `icon_slider`
4. `radial_menu`

这 `4` 个是当前最显眼的覆盖缺口，但不是 `a-0.6` 的全部工作量。

### 当前剩余缺口总账

当前最终发布视角下，仍存在以下系统性缺口：

1. final release matrix 虽已升级到 `a-0.6-final-release-v1`，但仍需继续接受最终文档和人工证据同步审计。
2. `keyboard` 仍是 runtime-first、manual-artifact-required 特例，不应被误写成 dedicated mapping/visible 已单独闭环。
3. `message_box` 仍保留 formal mapping exclusion 特例，不能与普通静态 widget 混写。
4. final release manual artifact truth-source 已补到 `24/24` demo 的 artifact existence 与 artifact-based visual observation；但该层仍不等于 live OS 窗口现场验收通过。
5. 中文发布文档目前仍分散在 `demo_guide / serial index / review / spec / plan`，还没有完全压缩成最终发布总入口。

### 完成定义

`a-0.6` 完成时至少要满足：

1. `26/26` 全控件进入 PicoUI public widget 集。
2. `26/26` 控件在 final release matrix 中全部收敛为 `full_parity_complete`。
3. 每个控件的 capability row 都已固定为 `support` 或 `reject-with-rationale`，不再停在 `deferred / incomplete_contract`。
4. final release matrix 已不再沿用 `a-0.3 current-15` schema。
5. 全量 demo catalog、runtime gate、backend mapping gate、visible gate、manual artifact truth-source、unit/contract proof set 全部与 `26` 控件对齐。
6. 全量中文发布文档、closeout 文档、发布说明、人工验收记录与当前代码态完全一致。
7. requirement-by-requirement 最终审计通过后，才允许把 `a-0.6` 写成完成。

### 主要风险

1. 继续把 `a-0.6` 误解成“只补 4 个控件”，会直接产出 `26/26 wrapped but not 26/26 complete` 的假完成。
2. `gauge / arc` 很容易只做视觉主路径，不做完整 getter/readback/contract。
3. `icon_slider / radial_menu` 很容易只做表层交互，不做复合导航语义。
4. `stable contract` 组很容易被误当成“只差文档”；实际上这 `12` 个控件都仍有真实 parity 缺口。
5. `minimal vertical slice` 组很容易被误当成“已经有 demo/unit/gate 就算完成”；实际上这 `6` 个控件离最终发布合同还差很远。
6. 如果 final release matrix 继续沿用 current-15 schema，就会把“当前盘点 truth-source”和“最终发布 verdict”混成一层。

## 与 a-0.3 的关系

`a-0.3` 当前只负责：

1. 把 current truth-source 做实。
2. 把 current-15 capability audit 做实。
3. 冻结 `a-0.3` closeout 标准。

`a-0.4 / a-0.5 / a-0.6` 当前只记录，不在本阶段展开 detailed spec / plan。

当前修正：

1. `a-0.4` 已不再是纯规划态，必须先以 `R7` 做真实 closeout。
2. 只有 `a-0.4` 的 matrix/gate/docs 收口后，才允许开始 `a-0.5`。

## 何时展开后续详细文档

只有在 `a-0.3` 满足以下条件后，才展开后续详细 spec 和 plan：

1. current public widget 总数明确。
2. current-15 capability audit 完成。
3. matrix / gate / docs 已对齐。
4. `a-0.3` closeout 标准冻结。
