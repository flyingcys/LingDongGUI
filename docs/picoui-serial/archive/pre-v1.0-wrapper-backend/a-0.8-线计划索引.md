## a-0.8 线定位

`a-0.8` 是 `v0.7 native-100` 的真实性修正线。

`v0.7` 已做到 `27/27` widget-like 控件进入 PicoUI 盘点，但不能诚实写成“100% 控件能力覆盖”。主要原因是 `v0.7` gate 仍以手写 inventory / matrix 自洽为主，没有从 `src/gui/ld*.h` 自动抽取全部 public API 后逐项证明 PicoUI public API、真实 backend 字段、unit、runtime/mapping/visible/manual 证据闭环。

`a-0.8` 的唯一目标：

1. 建立 `ldgui_public_api_inventory`，从 `src/gui/ld*.h` 自动抽取 public native API。
2. 建立 native API exhaustiveness gate，让遗漏能红。
3. 生成全量 `native API gap ledger`，先证明当前代码到底缺哪些能力。
4. 修复 ledger 中所有真实缺口；`text / image / window/layout / line_edit / keyboard / slider / button / qrcode` 只是已知高风险样本，不是完整范围。
5. 清理 `message_box / keyboard` 旧 special-case 证据冲突。
6. 禁止 temporary smoke layout 参与 full parity 结论。
7. 最终才能重新声明“100% 控件覆盖 + 对应控件 100% 能力覆盖”。

## 串行依赖

固定依赖链：

1. `R0`：native API inventory / extractor
2. `R1`：exhaustiveness matrix gate
3. `R2`：shared readback / resource / smoke-path policy
4. `R3`：全量 gap ledger 分批修复 A：base / layout / text / image / old widgets
5. `R4`：全量 gap ledger 分批修复 B：input / navigation / data widgets
6. `R5`：全量 gap ledger 分批修复 C：visual / instrument / composite / remaining widgets
7. `R6`：message_box / keyboard / manual artifact evidence 修复
8. `R7`：matrix / runtime / mapping / visible / manual gate closeout
9. `R8`：文档 closeout / release readiness review

顺序原因：

1. `R0/R1` 不先完成，后续修复无法证明“全量能力”。
2. `R2` 不先冻结 readback 和 smoke-path policy，各控件会继续各自定义完成口径。
3. `R3~R5` 的具体控件清单必须来自 `R0/R1` 生成的 gap ledger；不能只修 review 文档列出的样本。
4. `R6/R7/R8` 必须最后串行收口证据和文档。

8. 全套 contract / unit / runtime / mapping / visible / manual gate 通过。
