# PicoUI v1.1 重构设计

> 适用仓库：`/Users/cys/embedded/LingDongGUI`  
> 日期：`2026-06-07`  
> 目标版本：`v1.1`  
> 目标：将 PicoUI 重构为真正独立、轻量、单心智的小型 GUI，而不是 LingDongGUI wrapper、native/backend 叠层，或“小号 LVGL”

## 1. 背景

### 1.1 为什么要重构

当前 PicoUI 虽然已经推进到 `v1.0-native` 路线，但真实代码结构仍然混杂：

- `picoui/src/widgets/*.c` 大量直接依赖 `picoui/src/backend/ldgui/backend.h`
- 默认 `picoui` 构建链仍会把 `backend/ldgui` 作为 runtime support 链入
- `picoui/src/native/` 存在大量 native helper，但并未成为唯一控件真相源
- 很多控件 public API 仍通过 backend create / backend state / backend readback 工作

这导致 PicoUI 还不是一个真正干净的 GUI：

- 用户仍可能需要同时理解 `picoui`、`ld*`、ARM-2D、glue 层
- 目录层次和运行时 ownership 不一致
- “native-only” 设计目标与默认实现链条仍不完全一致

用户本轮重构的核心动机不是把目录挪到一起，而是把 PicoUI 收口成真正可独立理解和使用的一套小型 GUI，同时避免把它做成 LVGL 级别的大框架。

## 2. 总目标

本轮重构后，PicoUI 的最终链路应为：

```text
picoui public API -> picoui widgets -> picoui core(hidden) -> arm2d/port
```

并满足：

1. PicoUI 成为真正独立的小型 GUI，不再需要 `backend` / `native` / `ldgui wrapper` 心智。
2. PicoUI public API 允许重新整理，但必须保持 PicoUI 自己统一、简洁的接口风格。
3. `picoui/src/native/` 与 `picoui/src/backend/` 删除。
4. `picoui_app_*` public API 删除，不保留兼容层。
5. `src/gui/ld*.c` 不进入默认 PicoUI 运行链，只作为算法参考和迁移 oracle。
6. 从 LingDongGUI 复制来的代码必须改成 PicoUI 风格函数命名、参数形态、返回约定和注释风格。
7. PicoUI 保持“小型 GUI”定位，不演化成大型可扩展 GUI 平台。

## 3. 产品定位

### 3.1 PicoUI 不是什么

PicoUI 本轮重构后：

- 不是 LingDongGUI public API 的简单换皮
- 不是 `backend` + `native` + `widgets` 三层继续并存的折中方案
- 不是为了靠近 LVGL 而复制出一个“大而全 GUI”
- 不是多 backend、多 runtime mode、多套入口并存的平台

### 3.2 PicoUI 是什么

PicoUI 应该是：

- 一套干净、轻量、单路径的小型 GUI
- 一套把 LingDongGUI 已验证的控件算法与 ARM-2D 绘制能力重新整理后的统一 public GUI
- 一套对用户只暴露 `picoui` 一套概念和接口的系统

### 3.3 与 LVGL 的关系

参考 LVGL 的地方只限于：

- public 入口体验
- 适度统一的 widget API 组织方式
- `init / display / input / screen / timer_handler` 这类开发者模型

不参考 LVGL 的地方：

- 大型对象系统
- 复杂 style cascade
- 大型 theme engine
- 可插拔 backend 平台体系
- 庞大 runtime feature matrix

结论：PicoUI 的目标是“干净版、重构版、小型版的 LingDongGUI public GUI”，不是“小号 LVGL”。

## 4. 架构原则

### 4.1 对外没有 runtime 心智，对内保留最小基础设施

对外文档和开发者模型不再暴露 `runtime/native/backend` 分层。

但对内仍必须存在最小基础设施职责：

- display / input 注册
- active screen
- widget tree ownership
- layout 调度
- dirty / render / flush
- timer / tick / scheduler
- focus / navigation / input dispatch

这些职责收口到 `picoui/src/core/`，但不再作为单独 public 心智暴露给用户。

### 4.2 widgets 是控件唯一真相源

每个控件的 state、event reaction、geometry helper、render 逻辑必须由 PicoUI 自己持有。

禁止继续存在以下模式：

- `widget API -> backend create -> backend truth`
- setter 改 PicoUI 一份、backend 再改一份
- getter 读 backend mirror 而不是读 PicoUI 自己状态
- event 先进入旧 msg/signal 再折返到 PicoUI

### 4.3 ARM-2D 是绘制后端，不是 GUI 宿主

ARM-2D 负责：

- tile / fill / blend / image / text / pixel 级绘制
- flush 相关 host 接口

ARM-2D 不负责：

- widget tree
- state ownership
- layout ownership
- event ownership
- focus ownership

### 4.4 `src/gui` 是算法矿，不是源码母本

允许从 `src/gui/ld*.c` 复制：

- render 算法
- 几何公式
- 动画推进
- 局部 layout 算法
- 控件状态机

禁止直接复制或保留：

- `ldBase_t`
- `ld_scene_t`
- `ldMsg*`
- `SIGNAL_*`
- `arm_2d_control_node_t` tree ownership 模型
- LingDongGUI 内存入口
- LingDongGUI 风格 public/private API 壳

### 4.5 小型 GUI 优先

PicoUI 必须持续满足：

- 单人可读
- 单路径使用
- 薄抽象
- 低层数
- 低心智负担

如果某个设计会让 PicoUI 更像大型平台而不是小型 GUI，应默认拒绝。

## 5. 目标目录

重构后建议目录：

```text
picoui/include/picoui/
  *.h                  public API

picoui/src/core/
  display.c
  indev.c
  screen.c
  tree.c
  layout.c
  focus.c
  tick.c
  dirty.c
  render.c
  resource.c
  theme.c
  ...

picoui/src/widgets/
  window.c
  label.c
  button.c
  switch.c
  slider.c
  table.c
  ...

picoui/port/
  sdl/
  board/
```

删除：

```text
picoui/src/native/
picoui/src/backend/
```

`src/gui/ld*.c` 保留在仓库中，但不进入默认 PicoUI 运行链，也不再作为 PicoUI 私层目录的一部分。

## 6. Core / Widgets 职责切分

### 6.1 `core` 保留内容

`picoui/src/core/` 只保留公共基础设施：

- widget tree
  - parent / child / sibling
  - screen 归属
  - create / destroy / attach / detach
- 基础几何
  - x / y / width / height
  - absolute region
  - invalidation
- layout 调度
  - flex / grid / ignore-layout 公共调度
- focus / input dispatch
  - pointer / key / nav 命中和派发
- dirty / render pass
  - frame 流程
  - redraw region
  - flush 调度
- tick / scheduler
  - timer handler
  - 动画或定时回调推进
- display / indev / port glue
  - host 对接

`core` 不应理解某个具体控件的业务语义。

### 6.2 `widgets` 下沉内容

`picoui/src/widgets/` 下沉每个控件自己的：

- create / set / get public API
- 控件 state
- event reaction
- geometry helper
- arm2d draw / render
- layout hook

示例：

- button：pressed / checkable / key_value / text/image draw
- switch：checked / anim progress / knob-track geometry / value change
- slider：range / value / dragging / thumb-track geometry
- table：item width / item height / item region truth
- canvas：command buffer / render commands

### 6.3 从 `ldBase` 拆分策略

留在 `core`：

- tree 增删
- region / absolute position
- hidden / enabled / selectable / focusable 这类公共位
- layout dirty / render dirty
- input hit test
- timer / scheduler

下沉到 `widgets`：

- button toggle / press 语义
- switch animation / checked 语义
- slider value / drag 语义
- table item truth
- canvas command truth
- 各 widget 自己的绘制 helper

## 7. Public API 方向

本轮重构允许 public API 重新整理，不要求强兼容现有全部 `picoui_*` header 形态。

但必须满足：

1. 新接口保持 PicoUI 自己统一风格。
2. 不混入 `ld*` 命名。
3. 不暴露 `backend/native/runtime` 心智。
4. 用户不需要理解 LingDongGUI 或 ARM-2D 内部结构。
5. API 组织方式可适度向 LVGL 靠拢，但复杂度必须远低于 LVGL。

硬删除项：

- `picoui_app_*`

原则：

- 不保留第二入口
- 新 demo / docs / tests 不再以 `app` 模型组织

## 8. Demo 与开发者模型

上层开发模式应继续保持：

```c
picoui_init();
picoui_display_create(...);
picoui_indev_create(...);
picoui_screen_load(...);

while (1) {
    picoui_timer_handler();
}
```

但要强调：

- 这里只借开发者体验，不借大型框架复杂度
- `basic_widgets` 继续作为第一主样板
- demo 只表达用户意图，不承载适配补丁

## 9. 迁移规则

逐控件从 `src/gui` 借算法时，执行以下规则：

1. 允许复制 render / geometry / animation / layout 算法。
2. 禁止复制 `ldBase` / `ldScene` / `ldMsg` / `SIGNAL` / control-node 框架。
3. 复制进 PicoUI 后，必须立即改成 `picoui` 风格函数签名和实现组织。
4. 不允许保留 LingDongGUI 风格 wrapper 壳作为中间过渡层。
5. widget state 必须在 PicoUI 自己结构里成为 authority。
6. getter 必须读 PicoUI 自己 state，不读 backend readback。

## 10. 非目标

本轮重构不做：

1. 不追求复刻 LVGL 的大系统。
2. 不追求一次性把所有视觉细节做到像素级对齐。
3. 不要求保留现有全部 public API 兼容。
4. 不把 `src/gui` 整体搬进 PicoUI 后再慢慢清理。
5. 不引入更多私层目录来替代 `native/backend`。

## 11. 建议执行阶段

建议新开一条 `clean-picoui` 线，而不是继续沿旧 `P0-P8` 阶段直接续写。

### 11.1 `C0` 架构冻结

冻结：

- 目标目录
- 删除项
- public API 重整方向
- `src/gui` 迁移规则
- `small GUI` 复杂度上限

### 11.2 `C1` core 最小骨架

先建立最小可运行 `core`：

- tree
- screen / display / input
- tick / timer handler
- dirty / render pass
- widget base state

### 11.3 `C2` vertical slice

只跑通一条最小真实链路：

- screen / window
- label
- button
- pointer / key input
- basic render / flush

证明新链已经是：

```text
api -> widgets -> core -> arm2d/port
```

### 11.4 `C3` layout 与公共 widget 机制

补齐：

- flex / grid
- focus / selectable
- style / theme 最小集合
- 通用 text / image / font helper

### 11.5 `C4` 逐控件迁移

逐控件从 `src/gui` 借算法，迁入 PicoUI widgets：

- checkbox / switch / slider
- text / image / list / background
- table / graph / calendar / clock
- 其余扩展控件

### 11.6 `C5` 清场与 release gate

最后完成：

- 删除旧构建残留
- 更新 demo
- 更新 docs
- 重建测试矩阵
- 确认默认 `picoui` target 不再碰 `native/backend`
- 确认默认 PicoUI 运行链不再依赖 `ld*.c`

## 12. 验证原则

每阶段都应以 fresh verification 为真相。

重点验证：

1. 默认 `picoui` target 是否还链接 `native/backend`
2. widget truth 是否仍依赖 backend mirror/readback
3. demo / docs 是否只讲 PicoUI 一套心智
4. 从 `src/gui` 借来的代码是否已经完全改成 PicoUI 风格
5. PicoUI 是否仍保持小型 GUI 的复杂度边界

## 13. 风险与应对

### 13.1 风险 1：把 `src/gui` 连同宿主骨架一起搬进来

后果：

- 旧 LingDongGUI 心脏改名后继续存在
- PicoUI 只是换皮，不是真正独立 GUI

应对：

- 迁移规则硬性禁止复制 `ldBase/scene/msg/signal/control_node`

### 13.2 风险 2：为了 API 整理把 PicoUI 做大

后果：

- 复杂度接近 LVGL
- 丢失“小型 GUI”定位

应对：

- 每个 API 设计都以“是否增加额外心智负担”为审查标准

### 13.3 风险 3：先删旧层再建新骨架，导致大面积失稳

后果：

- build、test、demo 同时雪崩

应对：

- 严格按 `C1 -> C5` 推进
- 先立 core 最小骨架，再逐控件迁移，再最终清场

## 14. 结论

本轮重构的本质不是目录整理，而是 ownership 重构：

- PicoUI 对外只保留一套干净 public GUI 心智
- PicoUI 对内只保留 `core + widgets + port`
- `native/backend` 目录和心智全部移除
- `src/gui` 只作为算法来源，不作为运行时依赖
- 最终目标是“小型、直接、统一、独立”的 PicoUI，而不是 LingDongGUI wrapper 或大型 GUI 框架
