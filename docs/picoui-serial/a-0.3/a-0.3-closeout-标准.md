# a-0.3 Closeout 标准

## 目的

这份文件冻结 `a-0.3` 自己的完成定义。

它只回答：

1. `a-0.3` 做完时必须交付什么。
2. `a-0.3` 做完时哪些 gate 必须 fresh 通过。
3. `a-0.3` 做完时必须能回答哪些问题。
4. `a-0.3` 明确不等于什么。

## 必交文档

`a-0.3` closeout 时必须存在并保持一致：

1. `docs/tinyui-serial/a-0.3/README.md`
2. `docs/tinyui-serial/a-0.3/current-15-覆盖与分层真相源.md`
3. `docs/tinyui-serial/a-0.3/current-15-capability-audit.md`
4. `docs/tinyui-serial/a-0.3/a-0.3-closeout-标准.md`
5. `docs/superpowers/specs/2026-05-31-tinyui-a-0-3-truth-source-and-current-15-design.md`
6. `docs/superpowers/plans/2026-05-31-tinyui-a-0-3-truth-source-and-current-15-implementation.md`

## 必须 fresh 通过的 gate

`a-0.3` closeout 时至少要 fresh 运行并通过：

1. `python3 tests/tinyui/contract/check_tinyui_release_capability_matrix.py`
2. `git diff --check`

若 closeout 回合改动了更广的 contract/doc 同步脚本，也必须把对应脚本纳入 fresh 验证，但不能拿历史结果顶替当前回合证据。

## 必须能回答的问题

`a-0.3` closeout 时必须能基于当前 worktree 直接回答：

1. current TINYUI public widget 总数是多少。
2. current-15 分别是哪 `15` 个控件。
3. 仍未覆盖的是哪 `11` 个控件。
4. 哪 `4` 个控件仍可维持 `full parity complete`。
5. 哪 `5` 个控件只是 `stable contract but not full parity`。
6. 哪 `6` 个控件只是 `minimal vertical slice only`。
7. current-15 每个控件已完成什么、未完成什么。
8. machine-readable matrix、gate、中文文档是否使用同一套 current-15 术语。

## a-0.3 明确不等于什么

`a-0.3` 完成不等于：

1. TINYUI 已经 `26/26` 全控件覆盖。
2. current-15 已经全部 full parity。
3. `a-0.4 / a-0.5 / a-0.6` 的详细 spec 和 plan 已经展开。
4. 所有后续高耦合 shared-core 问题已经解决。
5. TINYUI 已经达到最终 release ready。

## 成功判定

只有当以下条件同时满足，才能说 `a-0.3` 完成：

1. `a-0.3` 当时的 current truth-source 已从旧 `9` 控件世界切换到 current-15。
2. current-15 全部进入 machine-readable matrix。
3. current-15 全部进入 capability audit。
4. `README / truth-source / capability audit / spec / plan / matrix / gate` 用词一致。
5. 本文件定义的 fresh gate 通过。

## 失败判定

以下任一情况都不能 closeout：

1. 仍无法准确回答 current public widget 总数。
2. 任一 current-15 控件状态不明，或 capability audit 缺段。
3. 文档说 `qrcode`，matrix 还写 `qr_code` 之类的口径漂移仍存在。
4. 把 `stable contract` 或 `minimal vertical slice` 提前写成最终 full parity。
5. 试图在 `a-0.3` 内顺手展开 `a-0.4+` 详细实施计划。
