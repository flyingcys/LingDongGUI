# demo4 残影/彩噪根因与修复总结

## 1. 现象概述

本次问题出现在 `examples/sdl` 的 `demo4`（`USE_DEMO == 4`，Layout demo）运行过程中。

直观看到的异常主要有两类：

1. 页面切换或局部更新后，屏幕上会出现像旧内容没有被擦干净一样的残影、叠影。
2. 某些区域会出现彩色噪点或脏块，看起来像是局部刷新把错误内容“留”在了 SDL 窗口上。

这两个现象一开始很容易被混在一起判断成“demo4 自身绘制不稳定”，但后续排查证明：一部分视觉现象其实是 demo 设计使然，真正的 bug 主要来自 SDL 呈现路径和 GUI 帧起始顺序两个位置。

## 2. 误判排除

在给根因下结论之前，先明确这几项不是 bug。

### 2.1 A/C 左右跳是 demo 设计，不是 bug

`demo4` 本身就是 layout / page 行为演示，页面内容会随 demo 逻辑发生切换或位移。排查时看到的 A/C 元素左右跳动，不代表渲染链残留旧帧，而是 demo 设计中的预期表现。

因此，不能把“元素位置变化”本身直接判成残影；真正要看的，是变化完成后旧位置是否还留下不该存在的像素。

### 2.2 左下 C 上的 `n` 是 UI 数据真值，不是残影

排查过程中，左下角 `C` 上方/附近出现的 `n` 容易被误看成上一帧残留字符。但从 UI 数据真值角度看，这个字符属于当前界面应显示的内容，不是 SDL backbuffer 被污染后留下的随机旧像素。

因此，这个 `n` 应归类为“当前 UI 数据的真实显示”，而不是“渲染残影证据”。

## 3. 两个真正根因

## 3.1 根因一：`user/Virtual_TFT_Port.c` 把 SDL renderer backbuffer 当持久画布使用

问题核心在 `user/Virtual_TFT_Port.c` 的 `VT_sdl_present_texture(...)`。

这个函数虽然只对 dirty rect 调用了：

- `SDL_UpdateTexture(texture, &tRect, ...)`

但在呈现阶段，旧实现曾尝试只做局部 `RenderCopy`。这种做法默认了一个前提：SDL renderer 的 backbuffer 会像持久画布一样保留上一帧内容，当前帧只需要把变更矩形重新盖上去即可。

这个前提不成立。

对 SDL renderer 来说，backbuffer 不是可以安全依赖的“长期存储画布”。如果只把局部 dirty rect 拷回 renderer，而没有先把整帧重新建立出来，那么未覆盖区域是否保持为预期内容并没有可靠保证。结果就是：

1. 旧帧像素可能继续留在窗口里，表现为残影。
2. 局部区域和未刷新的周边区域内容不一致，表现为彩噪、脏块或错误拼接。

本质上，dirty rect 只应该用于“更新 texture 的哪一块数据”，不应该直接等价成“renderer 也只需要保留性地补这一块”。

### 3.1.1 对应修复方式

修复思路是把“局部纹理更新”和“整帧呈现”分开：

1. 继续保留 `SDL_UpdateTexture(texture, &tRect, ...)`，让 dirty rect 只负责把变化内容写进 `texture`。
2. 在每次 present 前先执行 `SDL_RenderClear(renderer)`。
3. 再执行 `SDL_RenderCopy(renderer, texture, NULL, NULL)`，把完整 `texture` 重新拷到窗口。
4. 最后 `SDL_RenderPresent(renderer)`。

这样做之后，真正持久保存整帧内容的是 `texture`，而不是 SDL renderer 的 backbuffer；renderer 每一帧都只是把当前完整纹理重新显示出来，从而消除局部拷贝导致的残影和彩噪。

### 3.1.2 关键代码路径

- `user/Virtual_TFT_Port.c`
- 函数：`VT_sdl_present_texture(...)`
- 关键调用链：
  - `SDL_UpdateTexture(texture, &tRect, ...)`
  - `SDL_RenderClear(renderer)`
  - `SDL_RenderCopy(renderer, texture, NULL, NULL)`
  - `SDL_RenderPresent(renderer)`

## 3.2 根因二：`src/gui/ldGui.c` 里 page loop 晚于 frameStart，导致 layout 变更晚一帧生效

第二个真实根因在 `src/gui/ldGui.c` 的 `ldGuiFrameStart(ld_scene_t *ptScene)` 顺序。

这里的关键不是“有没有执行 page loop”，而是“它相对 frameStart 的执行时机”。如果 page loop 晚于 page/widget 的 `frameStart`，那么本帧刚刚产生的 layout 变更只能等下一帧才能真正反映到布局与绘制结果上。

这会带来两个直接后果：

1. 当前帧看到的是“旧布局 + 新逻辑正在准备”的混合状态。
2. 页面切换、位置更新、布局重排会出现一帧延迟，视觉上就像旧内容停留了一下，进一步放大“残影/脏帧”的观感。

也就是说，这个问题不一定单独制造彩噪，但它会制造“旧位置内容晚一帧消失”的现象，使用户更容易把 layout 延迟误判成渲染残影。

### 3.2.1 对应修复方式

修复方式是把 page loop 提前到 frameStart 之前，让当前帧的 layout 变更在同一帧内就完成生效。

正确顺序应为：

1. 先执行 page 级 `loop(ptScene)`。
2. 再执行 widget 的 `frameStart(ptScene, ptItem)`。
3. 最后执行 page 级 `frameStart(ptScene)`。

这样本帧的布局更新、控件位置变化和后续绘制会基于同一份最新状态，不再晚一帧落地。

### 3.2.2 关键代码路径

- `src/gui/ldGui.c`
- 函数：`ldGuiFrameStart(ld_scene_t *ptScene)`
- 关键顺序：
  - `ptScene->ldGuiFuncGroup->loop(ptScene);`
  - `((ldBase_t*)ptItem)->ptGuiFunc->frameStart(ptScene,ptItem);`
  - `ptScene->ldGuiFuncGroup->frameStart(ptScene);`

## 4. 修复与现象之间的对应关系

把这两个根因分开看，问题会更清楚：

- `user/Virtual_TFT_Port.c` 的修复，解决的是 SDL 呈现链把 backbuffer 当持久画布导致的真实残影和彩噪。
- `src/gui/ldGui.c` 的修复，解决的是 layout/page 状态更新晚一帧，导致旧内容多停留一帧的时序问题。

两者叠加时，用户会感觉 demo4 “又脏又拖尾”；拆开后则可以明确：一个是呈现面的问题，一个是帧时序的问题。

## 5. 验证方式

本次修复后的验证分成代码约束检查和现象回归两部分。

### 5.1 已加的 shell tests

1. `tests/check_stage_f_full_present.sh`
   - 目的：确保 `VT_sdl_present_texture(...)` 采用“dirty rect 更新 texture + full render present”的约束。
   - 核查点：
     - 必须存在 `SDL_RenderClear(renderer)`。
     - 必须存在 `SDL_RenderCopy(renderer, texture, NULL, NULL)`。
     - 不允许再出现 `SDL_RenderCopy(renderer, texture, &tRect, &tRect)` 这种局部 present 路径。
     - 保留 `SDL_UpdateTexture(texture, &tRect, ...)` 的 dirty rect 纹理更新。

2. `tests/check_stage_g_frame_start_order.sh`
   - 目的：确保 `ldGuiFrameStart(...)` 中 page loop 已经提前到 frameStart 之前。
   - 核查点：
     - 必须存在 page loop 调用。
     - 必须存在 page frameStart 调用。
     - 必须存在 widget frameStart 调用。
     - page loop 不能再晚于 widget/page 的 frameStart。

3. `tests/check_stage_h_partial_blit_stride.sh`
   - 目的：确保 partial dirty rect 从 framebuffer 拷到 SDL 前台缓存时，按正确 stride 跨行读取。
   - 核查点：
     - 必须存在 stride-aware 的局部 blit helper。
     - partial dirty rect 路径必须显式以 `VT_WIDTH` 作为源 framebuffer stride。
     - packed bitmap 路径也必须复用同一个 stride-aware helper。

### 5.2 当前仓库中的执行方式

在 `examples/sdl` 目录下执行：

```bash
rtk bash tests/check_stage_f_full_present.sh
rtk bash tests/check_stage_g_frame_start_order.sh
```

本次复核结果为：

- `PASS: present 路径满足 full render 约束`
- `PASS: 检测到 page loop 先于 frameStart 执行`
- `PASS: 检测到 stride-aware partial blit 修复`

### 5.3 现象回归关注点

除 shell tests 外，人工回归时建议重点看以下几点：

1. 页面切换后，旧位置不应留下持续性残影。
2. 局部变化区域周围不应出现彩色噪点或脏块。
3. layout 变化应当本帧生效，不应再出现明显“一帧后才归位”的感觉。
4. 继续区分 demo 设计动作和真正脏帧，避免把 A/C 跳动或左下 `C` 上的 `n` 误判成 bug。

## 6. 补充结论：demo0 与 demo4 不是完全同根因

后续继续排查 `USE_DEMO == 0` 的 legacy widget demo 后，确认 `demo0` 也会出现大面积残影/彩噪，但它和 `demo4` 不是完全同一种问题。

### 6.1 相同点

`demo0` 和 `demo4` 共用同一套 SDL 前端与 GUI 主循环，所以本文前面描述的两条修复对 `demo0` 依然成立：

1. SDL present 路径不能把 renderer backbuffer 当持久画布。
2. page loop 不能晚于 frameStart，否则会把状态变化拖到下一帧。

也就是说，`demo4` 的两条根因不是错的，只是**不足以单独解释 `demo0` 的大面积横向条纹**。

### 6.2 不同点

`demo0` 的视觉特征更明显：

- 问题区域通常更大。
- 画面更像成片横向彩线、扫描线、错误条带。
- 不只是“旧内容没擦干净”，而是“局部矩形整体读错像素”。

这说明 `demo0` 除了共享 SDL/render 时序风险外，还叠加了一个更底层的 dirty rect 上传 bug。

### 6.3 demo0 的直接根因：partial blit stride 错误

关键问题在：

- `user/Virtual_TFT_Port.c`
- `VT_Fill_Multiple_Colors(...)`

旧逻辑里，partial dirty rect 路径会把：

- “全屏 framebuffer 中 dirty rect 左上角地址”

传给 `VT_Fill_Multiple_Colors(...)`，但这个函数却按：

- “紧密 packed 的小矩形位图”

来读源数据。

这会导致跨行时没有按真实 framebuffer 宽度跳到下一行同列位置，而是直接沿着上一行后面的内存继续读。结果就是：

1. 下一行读成上一行后续数据。
2. 大矩形局部刷新时会出现横向条纹和彩噪。
3. dirty rect 越大，错误越明显。

### 6.4 为什么 demo0 更容易触发

`demo0`（legacy widget demo）里有多组周期更新控件，例如：

- `ldArc`
- `ldGauge`
- `ldDateTime`

这些控件持续产生 dirty region，SDL 侧又会把多个分离区域并成较大的包围盒，因此 stride 读错一旦发生，就会被放大成截图里那种大面积横向异常。

### 6.5 demo0 的修复方式

本次又补了一层修复：

1. 在 `user/Virtual_TFT_Port.c` 中新增 stride-aware 的局部拷贝 helper。
2. partial dirty rect 路径显式按 `VT_WIDTH` 作为源 framebuffer stride。
3. packed bitmap 路径继续保留，但统一复用同一个 stride-aware helper。

这样 partial dirty rect 拷贝时，就会从“源 framebuffer 下一扫描线同列位置”继续读，不会再把行尾后的连续内存误当成下一行像素。

### 6.6 最终归纳

更完整的结论应当是：

- `demo4`：主因是 SDL present 路径 + frameStart 时序。
- `demo0`：共享上述两层风险，但还额外叠加了 partial blit stride bug。

## 7. 经验总结

1. dirty rect 可以用来减少纹理更新量，但不能顺手把 SDL renderer backbuffer 当成持久画布。
2. 视觉上的“残影感”不一定全是渲染问题，UI 状态更新晚一帧同样会制造类似观感。
3. dirty rect 问题还要继续区分“区域算错”与“区域内容读错”：
   - `demo4` 更偏 present/backbuffer 与 frame 时序。
   - `demo0` 更偏 partial blit stride。
4. 做这类图形问题排查时，先把 demo 设计行为和真正异常分开，能显著减少误判。
5. 最稳妥的做法是同时补代码顺序约束和 shell 守护测试，避免后续回归把同类问题再引回来。
